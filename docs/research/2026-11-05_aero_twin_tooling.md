# Synthetic-data "digital twin" pipeline (Blender 4.2.1 + BlenderProc 2.8.0 on an Apple M3 or a cheap cloud GPU) that outputs COCO/YOLO labels for aircraft-skin-style defect detection on the TriNetra handheld (Pi 5 + AI HAT+ 2 Hailo-10H + IMX500 AI Camera)

(Research, 5 Nov 2026. Every finding carries its source; UNVERIFIED and (calc) are marked.)

## Summary

The recommended stack is Blender 4.2.1 LTS with BlenderProc 2.8.0, the latest release (22 Oct 2024). It pins Blender 4.2.1, downloads the macos-arm64 build automatically when Python is native arm64, and defaults to Cycles on Metal on macOS. Develop and run the pilot on the M3, then do the full render overnight on the M3 or for a few hours on a JarvisLabs L4 ($0.44/h). The alternatives fit worse. Omniverse Replicator/Isaac Sim needs x86 Linux/Windows with an RTX 4080-class GPU and does not support A100/H100. Kubric is pinned to Blender 2.93 in Docker. Unity Perception is discontinued. Infinigen generates natural and indoor worlds, not metal coupons. NVIDIA's own defect example (Replicator defectsgen, now archived) is just randomized normal-map scratch decals plus YOLOv8, which Blender can reproduce exactly. To be a digital twin of their device rather than a generic render, the scene must be built from measured data. The IMX500 nominal intrinsics (fx ≈ 3058 px, 65 µm/px at 200 mm (calc)) must be confirmed with a ChArUco calibration. The LED pods become camera-rigid lights placed from the Fusion 360 transforms. White, raking and UV are three keyframed light states. Render native-scale 1024x1024 windows of the 4056x3040 sensor rather than full 12 MP frames. Two physics checks change the plan. At F1.79 the depth of field at 200 mm is only about ±10 mm, so the 150-250 mm handheld range blurs fine scratches by 8-14 px (calc). On a flat plate the pod reflections land inside the region of interest (calc), and the twin should be used to choose standoff and tilt. Build each defect as procedural maps in plate-millimetre UV space (4096² texels ≈ 24 µm/texel), which gives exact mm ground truth. Dents and gouges use displacement, and scratches use bump plus roughness. Tight cracks are sub-pixel, so model the penetrant bleed-out indication on white developer. BlenderProc's built-in segmentation is per object, so texture defects need AOV/ID-pass masks (ScratchSim's method) or, on a flat plate, an exact homography projection. Cycles is RGB-only and cannot fluoresce, and the team's red azo dye is probably non-fluorescent, so the UV state should be violet light plus emission only on materials that a real 5-minute test shows glowing. Rendering 9,000 frames (3,000 scenes x 3 light states) should take about 14-24 h on the M3 (calc; the per-frame time is UNVERIFIED until the 20-frame pilot), about 6.5-9 h (~$3-4) on an L4, or about 5 h on an RTX 4090, which is limited by BlenderProc's per-frame overhead. The JPEG-only output is about 5-7 GB, but the Mac has only about 10 GB free (measured), so use an external SSD or cloud disk. Training should tile renders to 640 px at native scale (not Ultralytics' whole-image resize), pretrain YOLOv8n(-seg) on synthetic data, fine-tune on real tiles split by plate, and compile with Hailo DFC 5.1.0 plus Model Zoo v5.1.0 on a pinned Colab runtime. The published evidence (ScratchSim 2026, Fulir CVPRW 2023) says synthetic-only training underperforms real-only, and synthetic pretraining followed by real fine-tuning beats both. "Works directly in the real world like NVIDIA" should therefore be pitched as "simulation-pretrained, real-calibrated", and only classes they can physically make should be validated.

## Findings

- BlenderProc's latest release is v2.8.0, published 2024-10-22 (PyPI upload the same day), which 'upgrades to Blender 4.2.1'. The repo is still maintained, with PR merges on 2026-01-07. (https://github.com/DLR-RM/BlenderProc/releases ; https://api.github.com/repos/DLR-RM/BlenderProc/commits ; https://pypi.org/pypi/blenderproc/json)
- The BlenderProc installer is hard-pinned to blender-4.2.1 ('right now only support blender-4.2.1'). It downloads https://download.blender.org/release/Blender4.2/blender-4.2.1-macos-arm64.dmg unless platform.machine() contains 'x86', so an x86/Rosetta Python (e.g. old Anaconda) silently installs the Intel build. Issue #1070 shows exactly this on an M2 Pro. The team's Python reports arm64 (measured 2026-11-05). (https://raw.githubusercontent.com/DLR-RM/BlenderProc/main/blenderproc/python/utility/InstallUtility.py ; https://github.com/DLR-RM/BlenderProc/issues/1070)
- On macOS, BlenderProc's first run can fail with 'PermissionError: Operation not permitted' when it creates custom-python-packages inside Blender.app. The fix PR #1231 (tested on macOS 26.3) is still OPEN and unmerged (last update 2026-03-04). The known workaround is to allow the terminal to modify apps (App Management/Full Disk Access). (https://github.com/DLR-RM/BlenderProc/pull/1231 ; https://github.com/DLR-RM/BlenderProc/issues/768)
- bproc.renderer.set_render_devices() defaults to ['METAL'] on macOS 12.3+ and to ['OPTIX','CUDA','HIP'] on Linux/Windows. set_denoiser accepts 'INTEL' (OIDN) or 'OPTIX'. Helpers set_noise_threshold, set_max_amount_of_samples, set_light_bounces, enable_depth_output, enable_normals_output and enable_motion_blur (with rolling shutter) all exist. (https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/python/renderer/RendererUtility.py)
- BlenderProc's enable_segmentation_output assigns IDs per mesh object (obj.pass_index = index+1). Defects that exist only as textures or displacement on the plate object therefore get no separate instance masks. You need AOV/ID-pass masks, separate decal objects, or analytic projection. (https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/python/renderer/RendererUtility.py)
- bproc.writer.write_coco_annotations(output_dir, instance_segmaps, instance_attribute_maps, colors, color_file_format='PNG', mask_encoding_format='rle'|'polygon', jpg_quality=95, ...) skips idx 0 and category_id 0 as background. Light.set_energy/set_color/set_radius take a frame argument, so several light states can be keyframed into one render() call. (https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/python/writer/CocoWriterUtility.py ; https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/python/types/LightUtility.py)
- Relevant BlenderProc examples: advanced/coco_annotations, camera_depth_of_field, lens_distortion, entity_displacement_modifier, dust, material_randomizer, motion_blur_rolling_shutter, spotlight, calibration, multi_render; basics/camera_sampling, light_sampling, material_manipulation. The CLI 'blenderproc download haven' accepts --types/--categories/--resolution filters. (https://github.com/DLR-RM/BlenderProc/tree/main/examples ; https://github.com/DLR-RM/BlenderProc/blob/main/blenderproc/scripts/download_haven.py)
- ScratchSim (arXiv 2607.27065, Fraunhofer IGD / TU Darmstadt / TU Delft, 2026) is the closest template. It uses BlenderProc 2.8.0 on Blender 4.2.1 with Cycles PBR. Scratches are procedural 2D cubic-Bezier masks on an 8192² canvas that modulate roughness, colour, normals and a small negative displacement. Masks are exported with an AOV Output node, binarized and split into connected components, then written as COCO. Real-test results for YOLO26 mAP50: real-only 0.610, synthetic-only 0.451, synthetic plus 10% real mixed 0.507, and synthetic-to-real fine-tune 0.680-0.723. Fine, low-contrast scratches stayed hard for every strategy. The repo has no licence, so use it for reference only. (https://www.alphaxiv.org/abs/2607.27065 ; https://github.com/saptarshineil/ScratchSim ; https://api.github.com/repos/saptarshineil/ScratchSim)
- Fulir et al. (CVPRW 2023) cut dents (0.2-2 mm) and scratches (0.05-0.3 mm) directly into geometry and rendered masks with an emissive material. They also added unlabelled 'insignificant defects' so the model learns to ignore them. Synthetic-only models had lower recall than the real baseline, and fine-tuning on real images lifted performance 5-10% above it. They conclude the domain gap remains. (https://openaccess.thecvf.com/content/CVPR2023W/VISION/papers/Fulir_Synthetic_Data_for_Defect_Segmentation_on_Complex_Metal_Surfaces_CVPRW_2023_paper.pdf)
- Aerospace precedent: TU Delft BladeSynth pre-trained Scaled-YOLOv4 on synthetic engine-damage images and fine-tuned on real ones, and synthetic pre-training improved damage detection. A 2026 AIDAA paper (Mhatre et al.) uses mixed real and synthetic fuselage images for dent detection. Neither shows zero-shot sim-to-real. (https://repository.tudelft.nl/record/uuid:9a53f188-9999-41ca-8082-f819b35177e5 ; https://iris.unina.it/handle/11588/1060020)

## Recommendations

- STEP 0 - Decision: use Blender 4.2.1 + BlenderProc 2.8.0 with a custom generator script. Do not use Isaac Sim/Replicator (needs x86 plus an RTX 4080-class GPU, A100 unsupported, days of setup), Kubric (Blender 2.93 in Docker), Unity Perception (discontinued) or Infinigen (wrong domain). In the report, frame the work as 'NVIDIA-style domain-randomized simulation, reproduced on an Arm/Apple laptop', and cite NVIDIA's own defectsgen normal-map-decal approach as the analogue.
- STEP 1 - Install on the M3 (about 1 h). Free about 25 GB first or use an external SSD. Commands: `brew install uv && uv venv ~/venvs/bp -p 3.11 && source ~/venvs/bp/bin/activate && python -c 'import platform;print(platform.machine())'` (must print arm64), then `pip install blenderproc==2.8.0` and `blenderproc quickstart --blender-install-path /Volumes/SSD/blender` (downloads blender-4.2.1-macos-arm64), then `blenderproc pip install opencv-python-headless scipy`. If you get 'PermissionError ... custom-python-packages', allow your terminal in System Settings > Privacy & Security > App Management (or Full Disk Access) yourself and rerun. The alternative is the unmerged fix branch: `pip install git+https://github.com/silverl/BlenderProc@iss_768_macos_app_bundle_permissions` (third-party fork, review it first). Do not use the default pyenv Python 3.14.
- STEP 2 - Measure the real device before modelling (half a day). (a) Calibrate the IMX500 at full 4056x3040 with a printed ChArUco board at about 200 mm (OpenCV cv2.aruco.CharucoDetector + cv2.calibrateCamera) and save K and distortion. Nominal values are fx ≈ 3058 px, cx = 2028, cy = 1520 (calc). (b) Export from Fusion 360 every LED position and direction in the camera frame (toe-in 14°, UV tilt 16°) into rig.json. (c) With fixed exposure and AWB, photograph a clean plate at 200 mm in each light state, plus a white card under UV only to get the violet RGB the camera actually records. (d) Do the 5-minute UV test on penetrant and developer smears. (e) Download about 30 indoor HDRIs only: `blenderproc download haven ~/hdri --types hdris --categories indoor --resolution 1k`. Do not download all of cc_textures, because of disk space.
- STEP 3 - Build the twin scene (gen.py; days 1-2). (1) `import blenderproc as bproc` must be the first line; then bproc.init(); set_render_devices(desired_gpu_device_type=['METAL']) (['OPTIX'] in the cloud); set_max_amount_of_samples(96); set_noise_threshold(0.02); set_denoiser('INTEL'); set_light_bounces(glossy_bounces=4, max_bounces=6). (2) Camera: render a native-scale 1024x1024 window of the full sensor around the projected plate, using bproc.camera.set_intrinsics_from_K_matrix([[fx,0,cx-ox],[0,fy,cy-oy],[0,0,1]],1024,1024). This keeps 65 µm/px exactly, as in tiled inference on the Pi. Add bproc.camera.add_depth_of_field(focal_point_empty, fstop_value=1.79) at the calibrated focus distance. (3) Pose: d ~ U(185,215) mm for 80% of frames ('sharp') and U(150,250) mm for 20% (labelled for a 'retake/blur' gate); tilt about x and y ~ U(-15°,15°); roll ~ U(0,360°). Use the same cam2world for frames 0, 1 and 2. (4) Lights: for each LED in rig.json create bproc.types.Light('SPOT'), set_radius(1.5e-3), location = cam2world @ p_cam. Keyframe energy with set_energy(E, frame=k): frame 0 = both white pods; frame 1 = one pod only (raking) or room-only; frame 2 = UV pods on and white off, with HDRI strength keyframed down via bpy. Add 0-2 random overhead 'tube light' area lights at 4000-6500 K. Calibrate all light powers by matching histograms and hotspot shapes to the Step 2 photos, not by datasheet watts.
- STEP 4 - Plate material (brushed 'aircraft' aluminium; tune against the photos). The plate is 0.1 x 0.1 x 0.003 m (BlenderProc works in metres): a grid subdivided to about 1-2M vertices, with a Displace modifier driven by the per-scene height map. Use a Principled BSDF with Multiscatter GGX: Base Color (0.916,0.923,0.924), Metallic 1, Specular Tint (0.989,0.989,0.972), Roughness ~U(0.15,0.40), Anisotropic ~U(0.3,0.9), Anisotropic Rotation ∈ {0, 0.25} (brush direction), and Tangent from a Tangent node on the UV map. Add brush lines with a Noise texture mapped at scale (1, 300, 1) into Bump strength 0.02-0.08 and ±0.05 roughness. Randomize unlabelled distractors: fingerprints (roughness smudges), BlenderProc 'dust', marker ink, edge burrs and tube-light reflections. Following Fulir, these must not appear in the masks.
- STEP 5 - Defect generators in numpy, in plate-mm UV space (4096² over 100 mm = 24.4 µm/texel). Each scene gets 0-6 defects, with about 10% defect-free scenes. Save the seed and per-defect mm parameters, not the textures. Classes to validate on real parts: (a) punch_dent: a cone or spherical cap with D ~ U(0.5,2.5) mm, depth ~ U(0.1,0.6) mm and a +20-50 µm raised burr ring, applied by displacement; calibrate the D/depth ranges against the sectioned punch coupon. (b) scratch: cubic Bezier, length 3-60 mm, width 0.05-0.5 mm, V-profile 5-80 µm deep, as bump/normal plus a roughness increase. Geometry booleans are pointless at 65 µm/px. Use displacement only for gouges 0.5-2 mm wide and 0.1-0.5 mm deep. (c) pt_indication: these are separate 'developer scenes'. The developer is a white diffuse coat (albedo 0.85-0.92, roughness 0.9, speckle noise). Indications are lines 0.8-12 mm long and 0.2-1.5 mm wide (bloom; UNVERIFIED, so measure your plates), radiating ±20° from hole or notch edges with random branching, plus 0.3-1 mm dots. Take the red colour from photos of your kit. Add unlabelled non-relevant edge bleed-out. (d) Bare tight cracks: a hairline darkening with contrast scaled by width/pixel. Expect very low recall and say so. Synthetic-only stretch classes: corrosion (fBm/Voronoi white-grey powder, albedo 0.7-0.85, roughness 0.7-0.95, pits 0.1-1 mm across and 0.05-0.3 mm deep), smooth aircraft dents (Gaussian, 5-40 mm across, 0.1-1.5 mm deep), and rivets on a lap-joint coupon as mesh instances with category_id (missing = empty hole; 'smoking' = black streak decal). For these, BlenderProc's native per-object masks work.
- STEP 6 - Exact ground truth. For the flat plate, project the mm-space instance-ID map into each frame with the known homography, H = K·[r1 r2 t]·S, using cv2.warpPerspective with INTER_NEAREST. This is exact, costs no render time and uses the same plate-mm labelling already planned for real images. Displacement of 0.5 mm or less shifts labels by about 2 px or less at a 15° tilt (calc). For 3D parts (rivets, curved skins), use Cycles AOV masks (see ScratchSim's createScene.py for the wiring) or a second 1-4 spp emission 'ID render'. Write the masks: for each class, cv2.connectedComponents(mask>0.5) gives instances; build inst (int32, 0 = background) and attrs=[{'idx':i,'category_id':c,'name':...}]; then call `bproc.writer.write_coco_annotations(out, instance_segmaps=[inst]*3, instance_attribute_maps=[attrs]*3, colors=data['colors'], color_file_format='JPEG', jpg_quality=92, mask_encoding_format='polygon')`. Keep mm attributes (length_mm, width_mm, depth_mm, D_mm, distance_to_hole_mm, severity) in a sidecar JSON keyed by image_id for the severity rules and Llama-assistant tests.
- STEP 7 - UV state honesty. Render 395 nm as visible violet light, with the colour measured from the white card in Step 2. Add an Emission shader (strength proportional to analytic UV irradiance, P·cosθ/r², computed in numpy in UV space from the known LED poses) only on materials that glowed in the real UV test. If Penetrant-97 does not fluoresce, it should appear as a dark, absorbing line on violet-lit developer, not glowing. Keep a real UV photo next to a render in the report as twin validation.
- STEP 8 - Camera realism in post (numpy, applied before the JPEG save, or offline). Poisson-Gaussian noise with random gain, ±10% white-balance jitter, an unsharp mask (amount 0.3-1.0) to imitate the Pi ISP, 0-3 px linear motion blur, and JPEG quality 75-95. Optionally use the lens_distortion example with the calibrated distortion coefficients. Validate by comparing patch statistics (mean, std, FFT) of real and synthetic clean-plate crops.
- STEP 9 - Pilot, then the full render. Pilot: `time blenderproc run gen.py --n 20` gives the real seconds per frame and replaces this plan's 4-8 s assumption. Check labels with `blenderproc vis coco -i 0 -c coco_annotations.json -b out/coco_data` and put renders side by side with real photos. On 300 frames, also render each pose without defects and drop or flag labels whose difference-image contrast is below about 3 grey levels. This gives a detectability map (depth/width vs light state) for the report and stops invisible-defect label noise. Full run on the M3: `caffeinate -i blenderproc run gen.py --shard 0 --nshards 1 --n 3000 --out /Volumes/SSD/synth` (about 14-24 h, calc). Or on a JarvisLabs L4: `pip install blenderproc==2.8.0 && blenderproc quickstart`, then 2-3 shards in parallel with `nohup blenderproc run gen.py --shard $s --nshards 3 --gpu OPTIX ... &` (about 6.5-9 h, about $3-4, calc). Write JPEG plus COCO only. Keep depth and normals for 100 debug frames only.
- STEP 10 - Tile at native scale and convert. Do not let Ultralytics resize 1024 to 640, because that changes 65 to 104 µm/px and breaks the match with Pi tiling. Run `pip install sahi ultralytics`, then `python -c "from sahi.slicing import slice_coco; slice_coco('out/coco_data/coco_annotations.json','out/coco_data','tiles.json','tiles640',slice_height=640,slice_width=640,overlap_height_ratio=0.2,overlap_width_ratio=0.2,min_area_ratio=0.3)"`, then `python -c "from ultralytics.data.converter import convert_coco; convert_coco('tiles640','yolo_synth',use_segments=True,cls91to80=False)"`. Check the output folder layout, keep about 10% or fewer empty tiles, and split train/val by scene seed.
- STEP 11 - Real data and training. Capture 3 light states x several poses per plate. Label once per plate in mm and project with the homography. Split by plate (e.g. plates 1-3 train, 4 val, 5 test) and report per-defect Wilson 95% intervals. Train: `yolo segment train model=yolov8n-seg.pt data=synth.yaml imgsz=640 epochs=80 batch=32 device=0` (Colab/L4; device=mps also works on the M3, more slowly). Then fine-tune: `yolo segment train model=runs/segment/train/weights/best.pt data=real.yaml imgsz=640 epochs=60 lr0=0.002 freeze=10`. Run the ScratchSim-style ablation on the real test plate: real-only vs synth-only vs mixed vs synth-then-real. That table is the evidence for the digital-twin claim. Train a detection-only YOLOv8n from the same labels as the safer Hailo deployment, with seg as the upgrade.
- STEP 12 - Export to the AI HAT+ 2. Run `yolo export model=best.pt format=onnx imgsz=640 opset=11`. Then, on Colab pinned to the 2026.07 runtime (Python 3.12) with the DFC 5.1.0 wheel and `git clone -b v5.1.0 https://github.com/hailo-ai/hailo_model_zoo`, run `hailomz compile --ckpt best.onnx --calib-path calib_640/ --yaml hailo_model_zoo/cfg/networks/yolov8n_seg.yaml --classes <N> --hw-arch hailo10h --performance` (or yolov8n.yaml for detection). Use 1024 or more raw 0-255 calibration tiles, mostly REAL device tiles. On the Pi, check with `hailortcli parse-hef` / `hailortcli run`. Fallback: NCNN on the Pi CPU. Llama stays on the CPU through ExecuTorch.
- STEP 13 - QC assistant: no simulation training needed. Feed the sidecar JSON (class, mm sizes, location relative to holes and edges, light state) into a fixed prompt template for the on-device Llama. Use a few hundred synthetic cases as an automatic regression test of the advice against a project-defined, clearly 'illustrative' acceptance table. Real aircraft SRM limits are proprietary, so make no airworthiness claims.

## Risks

- The sim-to-real gap is real. Every cited study (ScratchSim, Fulir, BladeSynth) shows synthetic-only training below real-only, and the gains appear only after fine-tuning on real data. Claiming the model 'works directly in the real world like NVIDIA' without the real-plate ablation would be overselling to judges.
- The 4-8 s/frame M3 render time is an assumption anchored on benchmark ratios and old BlenderProc figures (UNVERIFIED). If the pilot shows over 15 s/frame, move the full render to an L4/A100, or cut samples to 64 or resolution to 640².
- Disk: the Mac has only about 10 GB free (measured), which is less than the Blender install plus HDRIs plus 5-7 GB of JPEG output plus about 11 GB of tiles. Without an external SSD or cloud disk the pipeline will fail mid-run. 16 GB of unified memory also limits the M3 to one BlenderProc process at a time.
- macOS BlenderProc install bugs: the unmerged PR #1231 permission error, and silently getting the x64 Blender (no Metal GPU) if Python runs under Rosetta. Blender 4.2 LTS reportedly reached end of maintenance in July 2026 (per a mirror of the release notes), so no further fixes will come. This is acceptable for an offline generator.
- Label noise: dents and fine scratches can be invisible under some light states or angles (Fulir, ScratchSim), but the masks still label them. This teaches the model to hallucinate. Mitigate with the difference-image visibility filter on the pilot set.
- Handheld optics: the ±10 mm depth of field at F1.79 (calc) and 8-14 px blur at 150/250 mm mean a model trained on sharp renders will miss defects in real blurry frames. The device needs a standoff guide or a blur/retake gate, and the synthetic set must include labelled blurry frames.
- Glare: pod hotspots on polished aluminium can saturate the region of interest (calc). If the twin is not matched to real photos, the model learns the wrong highlight statistics. Tune toe-in, tilt and exposure using the twin, and keep the 'no exotic hardware' rule (no cross-polarisers bought for this).
- UV and fluorescence: Cycles cannot simulate fluorescence, and the red azo dye is probably non-fluorescent. A faked glowing-red UV state would create a domain mismatch. Only fake emission for materials that a real test shows glowing.
- Ultralytics' imgsz resize silently changes the training scale (65 to 104 µm/px). Tiling at native scale with SAHI is mandatory, or the model will not match the Pi's tiled inference.
- The Hailo toolchain version chain (Pi HailoRT 5.1.1 needs DFC 5.1.0 plus Model Zoo v5.1.0; current Colab is Python 3.13) can fail independently of data quality. De-risk with a stock-model compile before the synthetic data is finished, and keep the NCNN CPU fallback.
- Scope and honesty: the team can physically make and validate only punch dents, scratches, notch or fatigue-crack PT indications and salt/vinegar corrosion on flat plates. Rivet, fretting and curved-skin classes are synthetic-only demos. Aircraft acceptance limits (SRM) are proprietary, so severity tables must be labelled illustrative.
- Licensing: ScratchSim's repo has no licence, so read it for reference and do not copy its code. Ultralytics YOLOv8 is AGPL-3.0, which is acceptable for a student challenge but must be stated in the report. Poly Haven HDRIs are fine to use.
- Schedule: 18 days remain. Building a procedural generator plus twin matching can easily take a week. Hold the 10 Nov cut-off and the 3-class minimum, and do not let synthetic-data work delay the real-data capture or the Hailo compile.
