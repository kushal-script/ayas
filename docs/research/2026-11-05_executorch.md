# Running Llama 3.2 on Raspberry Pi 5 (Cortex-A76, 8 GB) with ExecuTorch, as of 5 Nov 2026

SUMMARY: ExecuTorch 1.6.0 came out on PyPI on 4 Nov 2026. It pins torch==2.15.0 and supports Python 3.11 to 3.15. It ships ready-made wheels for Linux aarch64 (manylinux_2_28, which fits the Pi's Raspberry Pi OS Trixie: Python 3.13, glibc 2.41) and for macOS arm64. GitHub has not published 1.6.0 release notes yet: there are only rc tags and a release/1.6 branch, and the newest notes are for v1.5.1 (23 Sep 2026, torch 2.14.0). The key fact for the team: the Linux and macOS wheels include the LLM runner Python extension (`from executorch.extension.llm.runner import TextLLMRunner, GenerationConfig`, added in v1.2.0). It streams tokens through a callback and releases the GIL while generating. So the Pi needs no C++ build and no cross-compile: `pip install` in a venv on the Pi is enough. Use Llama 3.2 1B-Instruct SpinQuant (4-bit, group size 32, 8-bit activations and embeddings, XNNPACK with KleidiAI using the SDOT path). There is no newer small Llama: Meta's newest models on Hugging Face are the Llama 4 MoE models, far too big for a Pi. 3B is optional, if the measured speed allows it. Ready-to-run .pte files exist and need no Meta gating. software-mansion/Llama-3.2-ExecuTorch has a 1B SpinQuant XNNPACK .pte (about 1.0 GiB) plus tokenizer.json, built for ExecuTorch 1.4.1. ExecuTorch only guarantees an old .pte loads on the next minor release, so run that file on 1.5.1, not 1.6. executorch-community/Llama-3.2-1B-Instruct-SpinQuant_INT4_EO8-ET also exists, but it was built before 1.0, so the compatibility policy does not cover it. The team can skip export for the first working demo. For the report, they should re-export with export_llm on the Mac with 1.6.0, keeping the same versions on the Mac and the Pi. The Meta SpinQuant checkpoint they need is gated with manual approval, so request access today. The official Pi tutorial cross-compiles llama_main, but only on an x86_64 Linux host the team does not have. Its prebuilt binaries need glibc 2.38+, which is fine on Trixie and broken on Bookworm. Neither llama_main nor TextLLMRunner applies the chat template, so the caller must build the Llama 3 header and eot_id string. The KV-cache position also carries over between calls until reset(). I found no published 4-bit ExecuTorch tokens/s for Llama 3.2 on a Pi 5. Arm's INT8 (W8A8) 1B .pte measured 512 prompt tokens in 5.37 s (about 95 tok/s prefill, calc) with a 2,075 MB peak on a Pi 5. My bandwidth estimate (calc) puts 4-bit 1B decode below about 10-12 tok/s on a Pi 5, so the team must measure prefill and decode themselves for the report. The pitfalls: the export defaults max_seq_length and max_context_length to 128 unless the config sets them; a missing checkpoint gives random weights; the Pi throttles at 80-85 °C without the Active Cooler; and the Hailo/vision pipeline competes for the 4 cores.

## Findings
- [high] ExecuTorch 1.6.0 was uploaded to PyPI on 2026-11-04. It requires Python >=3.11,<3.16 and torch==2.15.0, torchao>=0.18.0 and pytorch-tokenizers. Wheels exist for cp311 to cp315 on manylinux_2_28_aarch64 (about 23 MB), macosx_14_0_arm64 (about 16 MB), x86_64 and win_amd64. (https://pypi.org/project/executorch/1.6.0/)
- [high] The newest published GitHub release is v1.5.1 (2026-09-23). Before it came v1.5.0 (2026-09-16), v1.4.1 (2026-08-14), v1.4.0 (2026-08-07), v1.3.1 (2026-05-29) and v1.2.0 (2026-04-01). 1.6.0 has only v1.6.0-rc1 to rc4 tags and a release/1.6 branch (last commit 2026-11-04); its release notes are not published yet. (https://github.com/pytorch/executorch/releases)
- [high] ExecuTorch 1.5.1 wheels support Python 3.10 to 3.14, including manylinux_2_28_aarch64. Its torch_pin.py sets TORCH_VERSION = 2.14.0; for 1.6 it is 2.15.0. (https://github.com/pytorch/executorch/blob/v1.5.1/torch_pin.py)
- [high] A maintainer closed the request for a Linux aarch64 pip package on 2026-09-18 after installing the ARM64 wheel with pip. Earlier, pip on a Pi 5 had found no matching distribution. (https://github.com/pytorch/executorch/issues/10651)
- [high] The wheel build preset sets EXECUTORCH_BUILD_EXTENSION_LLM_RUNNER=ON for both Darwin and Linux, so the published wheels include the extension executorch.extension.llm.runner._llm_runner. The v1.2.0 notes list it as Pybindings for TextLLMRunner. (https://github.com/pytorch/executorch/blob/release/1.6/tools/cmake/preset/pybind.cmake ; https://github.com/pytorch/executorch/releases/tag/v1.2.0)
- [high] The Python API is TextLLMRunner(model_path, tokenizer_path, data_path=None) with .generate(prompt, config, token_callback, stats_callback), .prefill, .stop, .reset and .get_vocab_size. GenerationConfig(echo=True, max_new_tokens=-1, warming=False, seq_len=-1, temperature=0.8, num_bos=0, num_eos=0). Stats exposes ms timestamps and to_json_string(). The README says the C++ and Python LLM runner APIs are experimental. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/_llm_runner.pyi ; https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/README.md)
- [high] The pybindings release the GIL during generate and take it back only for the token and stats callbacks. A Python UI or worker thread can therefore stream tokens without freezing the rest of the app. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/pybindings.cpp)
- [high] The runner README says to import `executorch.extension.llm.custom_ops.custom_ops` (KV-cache and SDPA kernels) and `executorch.kernels.quantized` once per process before loading an LLM .pte. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/README.md)
- [high] The CPU-only index has torch-2.15.0+cpu and executorch-1.6.0+cpu wheels for manylinux_2_28_aarch64 (cp311 to cp315). The docs give `pip install executorch==1.6.0 torch==2.15.0 --index-url https://download.pytorch.org/whl/cpu --extra-index-url https://pypi.org/simple`. The PyPI torch 2.15.0 metadata lists nvidia-*-cu13 dependencies on Linux. (https://download.pytorch.org/whl/cpu/torch/ ; https://github.com/pytorch/executorch/blob/release/1.6/docs/source/using-executorch-cpp.md ; https://pypi.org/pypi/torch/2.15.0/json)
- [high] The ExecuTorch Llama 3.2 4-bit scheme puts 4-bit groupwise weights (group 32) with 8-bit dynamic activations in the linear layers, 8-bit per-channel weights on the classifier and 8-bit per-channel embeddings. The README says 1B/3B are sensitive to plain post-training quantization, so SpinQuant or QAT+LoRA is recommended. (https://github.com/pytorch/executorch/blob/main/examples/models/llama/README.md)
- [high] Measured on a OnePlus 12 phone (not a Pi), prompt 64, with KleidiAI. 1B SpinQuant: 50.2 tok/s decode, 260.5 tok/s prefill, 1,083 MiB .pte, 1,921 MiB RSS. 1B QAT+LoRA: 45.8 tok/s, 252.0 tok/s, 2,255 MiB RSS. 3B SpinQuant: 19.7 tok/s, 89.7 tok/s, 2,435 MiB, 3,726 MiB. 1B BF16: 19.2 tok/s, 3,185 MiB RSS. (https://github.com/pytorch/executorch/blob/main/examples/models/llama/README.md)
- [high] No newer small Llama exists. The newest meta-llama models on Hugging Face are Llama-Prompt-Guard-2, Llama-Guard-4-12B and the Llama-4 Scout/Maverick 17B-active MoE models (April 2025). ExecuTorch 1.6's export ModelType includes llama3_2; the Llama 4 MoE models are not practical on an 8 GB Pi. (https://huggingface.co/meta-llama ; https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/export/config/llm_config.py)
- [high] The Meta repos use manual gating. meta-llama/Llama-3.2-1B-Instruct contains original/consolidated.00.pth (2.47 GB), original/params.json, original/tokenizer.model, model.safetensors and tokenizer.json. meta-llama/Llama-3.2-1B-Instruct-SpinQuant_INT4_EO8 contains consolidated.00.pth (1.62 GB), params.json and tokenizer.model. The 3B SpinQuant checkpoint is 3.96 GB. (https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct-SpinQuant_INT4_EO8)
- [high] The ungated prebuilt software-mansion/Llama-3.2-ExecuTorch has 1b/xnnpack/llama_3_2_1b_xnnpack_spinquant.pte (about 1.0 GiB), 3b/xnnpack/llama_3_2_3b_xnnpack_spinquant.pte (about 2.2 GiB), tokenizer.json and tokenizer_config.json. The model card says the files are built for the ExecuTorch v1.4.1 runtime. 1B metadata: max_seq_len 2048, max_context_len 16384, bos 128000, eos [128009, 128001], use_kv_cache and use_sdpa_with_kv_cache true. The 3B context is 4,096. Last updated 2026-10-14. (https://huggingface.co/software-mansion/Llama-3.2-ExecuTorch)
- [high] The ungated prebuilt executorch-community/Llama-3.2-1B-Instruct-SpinQuant_INT4_EO8-ET has the .pte (1.135 GB), tokenizer.model and params.json. A QLORA_INT4_EO8 sibling (1.18 GB) also exists. Both were last modified 2025-04-10 and exported with the old export_llama CLI (`--preq_mode 8da4w_output_8da8w --preq_group_size 32 --max_seq_length 2048 --max_context_length 2048 --use_spin_quant native`) from a pre-1.0 ExecuTorch. Whether 1.5 or 1.6 can load them is UNVERIFIED. (https://huggingface.co/executorch-community/Llama-3.2-1B-Instruct-SpinQuant_INT4_EO8-ET)
- [high] Compatibility policy: a .pte loads on a runtime at least one later minor release newer (for example, 1.2.0 to 1.3.0). Forward compatibility is not guaranteed. So the 1.4.1 file is covered on 1.5.x, and 1.6 only 'possibly'. (https://github.com/pytorch/executorch/blob/main/runtime/COMPATIBILITY.md)
- [high] Export configs in 1.6. llama_xnnpack_spinquant.yaml sets preq_mode preq_8da4w_out_8da8w, preq_group_size 32, preq_embedding_quantize 8,0, metadata bos 128000 / eos [128009,128001], use_sdpa_with_kv_cache, use_kv_cache, dtype fp32, max_seq_length 2048, max_context_length 2048, use_spin_quant native, xnnpack enabled with extended_ops. llama_xnnpack.yaml (plain PTQ) sets qmode 8da4w, group_size 128, embedding_quantize 4,32 and leaves the export lengths unset. llama_xnnpack_qat.yaml adds use_qat and use_lora 16. (https://github.com/pytorch/executorch/tree/release/1.6/examples/models/llama/config)
- [high] ExportConfig defaults are max_seq_length=128 and max_context_length=128. If base.checkpoint is empty, a Llama model gets random weights. Valid qmode values include int8, 8da4w, 8da4w-gptq, torchao:8da(N)w and torchao:fpa(N)w. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/export/config/llm_config.py)
- [high] The documented export command is `python -m executorch.extension.llm.export.export_llm --config <yaml> +base.model_class=llama3_2 +base.checkpoint=<consolidated.00.pth> +base.params=<params.json>`. The Llama README says it was tested on macOS M1/M2 and Linux. (https://docs.pytorch.org/executorch/stable/llm/export-llm.html ; https://github.com/pytorch/executorch/blob/main/examples/models/llama/README.md)
- [high] The official 'ExecuTorch on Raspberry Pi' tutorial (1.6 docs) requires a Linux x86_64 host (Ubuntu 20.04+ or CentOS Stream 9+). It clones release/1.6, runs `examples/raspberry_pi/setup.sh pi5` to cross-compile llama_main (about 6.1 MB) and libllama_runner.so, and runs `./llama_main --model_path ./llama3_2.pte --tokenizer_path ./tokenizer.model --seq_len 128 --prompt ...` with LD_LIBRARY_PATH set. It gives no tok/s figures. It says the binaries need GLIBC 2.38 and CXXABI_1.3.15, which Bookworm (glibc 2.36) lacks. (https://docs.pytorch.org/executorch/stable/raspberry_pi_llama_tutorial.html)
- [high] setup.sh downloads arm-gnu-toolchain-14.3.rel1 (glibc 2.40, GCC 14 libstdc++). Issue #24228 (2026-10-28) and the still-open PR #24345 propose building against the target OS's glibc. (https://github.com/pytorch/executorch/issues/24228)
- [high] Debian trixie (the base of Raspberry Pi OS Trixie) ships libc6 2.41 and python3 3.13.5. The cp313 aarch64 wheels and the tutorial's glibc-2.38 binaries both work on it. (https://packages.debian.org/trixie/libc6 ; https://packages.debian.org/trixie/python3)
- [high] Arm's Learning Path 'Run Llama 3 on a Raspberry Pi 5 using ExecuTorch' (updated 14 Aug 2026) exports and builds inside a Raspberry Pi OS Docker container on an Arm Linux host. It uses Llama 3.1 8B with -qmode 8da4w --group_size 128 --embedding-quantize 4,32, runs with --cpu_threads=4 and gives no tok/s. It says the 8B export runs out of memory with 32 GB RAM or less. (https://learn.arm.com/learning-paths/embedded-and-microcontrollers/rpi-llama3/llama3/)
- [high] llama_main flags in 1.6: --model_path, --data_paths, --tokenizer_path, --prompt, --prompt_file, --temperature (0 = greedy argmax), --seq_len (deprecated), --max_new_tokens, --cpu_threads (-1 = number of performant cores), --num_bos, --num_eos (both default 0), --warmup, --ignore_eos, --etdump_path, --method_name. The prompt goes to the tokenizer unchanged; main.cpp applies no chat template. (https://github.com/pytorch/executorch/blob/release/1.6/examples/models/llama/main.cpp)
- [medium] Native build presets: `cmake --workflow llm-release` (Release build, install to cmake-out), then `cd examples/models/llama && cmake --workflow --preset llama-release`, which produces cmake-out/examples/models/llama/llama_main. The llm preset turns on XNNPACK, optimized, quantized and LLM kernels and the LLM runner. Linux aarch64 is not on the 'tested' host list, and build time on a Pi 5 is UNVERIFIED. (https://github.com/pytorch/executorch/blob/release/1.6/CMakePresets.json ; https://github.com/pytorch/executorch/blob/release/1.6/docs/source/using-executorch-building-from-source.md)
- [medium] The 1.6 wheel's C++ SDK (find_package(executorch)) offers runtime, kernels_optimized, backend_xnnpack, threadpool, etdump, kernels_quantized and kernels_torchao (aarch64) components. No LLM-runner component is listed, so llama_main still needs a source build. (https://github.com/pytorch/executorch/blob/release/1.6/docs/source/using-executorch-cpp.md)
- [high] The tokenizer loader tries a Hugging Face tokenizer.json first, then tiktoken (Llama 3 tokenizer.model), then the llama2c BPE format. The tutorial says the json parse_error.101 warning seen when you pass tokenizer.model can be ignored. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/llm_runner_helper.cpp ; https://docs.pytorch.org/executorch/stable/raspberry_pi_llama_tutorial.html)
- [high] Llama 3.2 special tokens: 128000 <|begin_of_text|>, 128001 <|end_of_text|>, 128006 <|start_header_id|>, 128007 <|end_header_id|>, 128008 <|eom_id|>, 128009 <|eot_id|>. The HF eos_token is <|eot_id|>. ExecuTorch's own Python runner builds the chat string as <|begin_of_text|><|start_header_id|>system<|end_header_id|>\n\n{sys}<|eot_id|><|start_header_id|>user<|end_header_id|>\n\n{msg}<|eot_id|><|start_header_id|>assistant<|end_header_id|>. (https://huggingface.co/software-mansion/Llama-3.2-ExecuTorch/blob/main/tokenizer_config.json ; https://github.com/pytorch/executorch/blob/release/1.6/examples/models/llama/runner/generation.py)
- [medium] The pytorch tokenizers BPE base class turns special-token strings in the prompt text into their single IDs (all special tokens are allowed). A formatted chat string therefore tokenizes correctly. If the string already contains <|begin_of_text|>, keep num_bos=0. (https://github.com/meta-pytorch/tokenizers/blob/main/src/bpe_tokenizer_base.cpp)
- [high] TextLLMRunner keeps the KV-cache position (pos_) across generate() calls. When max_seq_len >= max_context_len, it fails if pos_ + prompt tokens >= max_context_len, so call reset() between independent prompts. The runner splits prompts longer than max_seq_len into prefill chunks. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/text_llm_runner.cpp)
- [high] The default thread count is the number of performant cores (4 on a Pi 5), capped on Linux by the process's CPU affinity mask, so taskset limits it. Python can call executorch.extension.pybindings.portable_lib._unsafe_reset_threadpool(n) and _threadpool_get_thread_count(). (https://github.com/pytorch/executorch/blob/release/1.6/extension/threadpool/threadpool.cpp ; https://github.com/pytorch/executorch/blob/release/1.6/extension/pybindings/portable_lib.py)
- [high] KleidiAI kernels are on by default in XNNPACK builds (EXECUTORCH_XNNPACK_ENABLE_KLEIDI ON). ExecuTorch 0.7+ added an SDOT-based int4 path that PyTorch says enables Llama 3.2 on the Raspberry Pi 5. I8MM kernels target Armv8.6+. (https://github.com/pytorch/executorch/blob/release/1.6/tools/cmake/preset/default.cmake ; https://pytorch.org/blog/bringing-generative-ai-to-the-masses-with-executorch-and-kleidiai/)
- [high] Arm's prebuilt Arm/llama3-2-1b-instruct-int8-xnnpack-executorch-raspberrypi5 (INT8 W8A8 dynamic with AWQ, model.pte 1,763.71 MB, ExecuTorch 1.1.0, measured on a Pi 5 16 GB) reports prompt 512, generation 1, 30 runs: prefill 5,372 ms, p50 end-to-end 374.72 ms, '2.67 tokens/sec', 2,074.73 MB peak memory. HellaSwag is 61% versus a 62% baseline. (https://huggingface.co/Arm/llama3-2-1b-instruct-int8-xnnpack-executorch-raspberrypi5)
- [medium] From the Arm INT8 card: 512 tokens / 5.372 s = about 95 tok/s prefill on a Pi 5. The '2.67 tok/s' equals 1000/374.72 ms, i.e. one over the p50 latency with generation length 1, so it is not a real decode benchmark. The card itself is internally inconsistent: its p50 end-to-end latency is shorter than its prefill time. (calc)
- [high] Same-device reference from Arm's llama.cpp card: Qwen3-0.6B Q4_K_M on a Pi 5 with 4 threads, prompt 512 and 128 new tokens, gives 25.26 tok/s, TTFT 3,636 ms and 946 MB peak. (https://huggingface.co/Arm/qwen3-0-6b-base-q4-k-m-llamacpp-raspberrypi5)
- [medium] I found no published ExecuTorch prefill/decode tok/s for 4-bit Llama 3.2 1B or 3B on a Pi 5. The only ExecuTorch Pi 5 LLM numbers I found are an old report of 4-bit Llama3-8B at about 2 tok/s and a Gemma-4-E2B custom export at 0.7 to 0.87 tok/s; the Gemma export did not use the optimized Llama path. (https://dev-discuss.pytorch.org/t/run-llama3-8b-on-a-raspberry-pi-5-with-executorch/2048 ; https://github.com/bamb00boy/Gemma4_executorch_deployment)
- [low] Decode ceiling estimate for 1B SpinQuant on a Pi 5. Bytes read per token: 4-bit linear layers about 0.49 GB, plus scales about 0.06 to 0.12 GB, plus the 8-bit output layer about 0.26 GB, about 0.87 GB in total. Peak LPDDR4X-4267 bandwidth on an assumed x32 bus is 17.1 GB/s. At 50-60% efficiency (UNVERIFIED assumption) decode tops out around 10-12 tok/s, so expect about 5-10 tok/s. 3B (about 2.1 GB per token) would top out around 4-5 tok/s. Prefill for 1B should be about 50-100 tok/s, consistent with Arm's INT8 95 tok/s. (calc)
- [high] The Pi 5 has a 2.4 GHz quad-core Cortex-A76 and LPDDR4X-4267, and needs a 5 V 5 A USB-C supply (27 W PSU). (https://www.raspberrypi.com/products/raspberry-pi-5/)
- [high] The Pi 5 throttles the Arm cores progressively between 80 and 85 °C, and at 85 °C throttles both the Arm cores and the GPU. The Active Cooler fan starts at 60 °C, speeds up at 67.5 °C and runs at full speed at 75 °C. (https://www.raspberrypi.com/documentation/computers/raspberry-pi.html ; https://www.raspberrypi.com/news/heating-and-cooling-raspberry-pi-5/)
- [high] The AI HAT+ 2 (Hailo-10H, 40 TOPS INT4, 8 GB on-board RAM, $200) is designed to fit on a Pi 5 with the Active Cooler in place, using a 16 mm stacking header, and comes with an optional heatsink. (https://www.raspberrypi.com/products/ai-hat-plus-2/)
- [high] vcgencmd get_throttled bits: 0x1 undervoltage, 0x4 currently throttled, 0x8 soft temperature limit. `measure_temp`, `measure_clock arm`, and the Pi-5-only `pmic_read_adc` (per-rail volts and amps) are all documented. (https://www.raspberrypi.com/documentation/computers/os.html)
- [high] The runner prints the line 'PyTorchObserver {json}' with prefill_token_per_sec, decode_token_per_sec, prompt_tokens, generated_tokens, model_load_start/end_ms, inference_start/end_ms, prompt_eval_end_ms and first_token_ms. Python Stats.to_json_string() returns the same JSON. (https://github.com/pytorch/executorch/blob/release/1.6/extension/llm/runner/stats.h)
- [high] The Llama 3.2 Community License requires anyone who distributes Llama Materials, or a product containing them, to prominently display "Built with Llama". (https://huggingface.co/executorch-community/Llama-3.2-1B-Instruct-SpinQuant_INT4_EO8-ET)

- [medium] Alternative export path: optimum-executorch 1.1.0 (Feb 2026, pins transformers==5.0.0rc1), e.g. `optimum-cli export executorch --model meta-llama/Llama-3.2-1B-Instruct --task text-generation --recipe xnnpack --use_custom_sdpa --use_custom_kv_cache --qlinear 8da4w --qembedding 8w`. It does not support SpinQuant; export_llm is the optimized path for Llama. (https://github.com/pytorch/executorch/blob/release/1.6/docs/source/llm/export-llm-optimum.md ; https://pypi.org/project/optimum-executorch/)
